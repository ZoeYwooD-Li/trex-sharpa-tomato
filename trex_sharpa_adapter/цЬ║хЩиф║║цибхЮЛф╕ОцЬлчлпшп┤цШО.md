# 从数采工程找到的模型与参考帧

已阅读用户提供的 `gello_upper_body_teleop.zip`。本次用它作为数采实现和模型来源；没有运行其中的硬件控制程序。

| 项目内文件 | 确认的信息 |
|---|---|
| `adapters/pico/assets/dual_fr3/dual_fr3_kinematics.urdf` | 完整双臂名义关节链；每臂 7 个转动关节，另有 link7→link8 固定变换 |
| `ros_ws/src/teleop_core/teleop_core/contract.py` | `left/right_fr3v2_joint*` 指令名规范化为数据的 `left/right_fr3_joint*`，顺序不变 |
| `config/workcell/current.yaml` | 当前左右机械臂控制配置使用 FR3，外部 ROS 描述路径为 `fr3/fr3.urdf.xacro` |
| `apps/arm_ui/runtime.py` | `tool_frame()` 返回每臂 `..._link8` |
| `adapters/pico/src/pico_bimanual_franka_teleop/ik.py` | Pico 的 `END_EFFECTOR_FRAMES` 选择 `..._link7`，与机械臂界面不同 |
| `portable_deps/litchi_hardware/src/litchi_hardware/hardware/sharpa/schema.py` | 22 关节 SDK 顺序、单位 rad，与数据列一致 |
| 同目录的 `sdk_driver.py`、`tactile.py` 及 ROS `messages.py` | 关节角与 SDK F6 原样进入驱动/ROS 路径，没有额外角度或力矩换算 |

模型本体、相关代码摘存和内容 SHA256 已随适配包保存；见 `robot/`、`collection_evidence/`、`collection_reference.json`。原 FR3 描述的许可证及 NOTICE 也保留在 `robot/`。

本次数据适配选择以下明确约定：

| 左右臂 | base link | tip link | URDF 关节 |
|---|---|---|---|
| 左 | `left_fr3v2_link0` | `left_fr3v2_link8` | `left_fr3v2_joint1…7` |
| 右 | `right_fr3v2_link0` | `right_fr3v2_link8` | `right_fr3v2_joint1…7` |

这是以法兰为参考的离线动作定义。GELLO 当时直接发送关节目标，没有一个必须恢复的 Sharpa 指尖 TCP。因此不需要为采摘另外定义虚构的抓取点，也不需要手掌安装偏移来计算法兰位姿。部署动作还原及 IK 要使用同一个 link8。

Pico 的 link7 不能直接替换进来：URDF 定义 link8 相对 link7 沿局部 z 方向平移 0.107 米，旋转相同。旋转动作时，两点的平移轨迹不同。脚本已验证此固定变换。

模型的世界→左右底座标定与旧 ROS 双臂 CAD 安装描述不同。本适配使用各臂自己的 link0，且动作是块首帧局部 delta-base；共同的世界→底座刚体变换在这项计算中抵消。验证已对比 `lychee_root` 和各自 `link0` 的结果，动作一致。因此不会把 Pico 的世界安装标定当作新的数采标定使用。

检查结果见 `fr3_validation.json`：

- 左右臂各 64 组随机合法配置，与独立 SciPy FK 的矩阵最大差约 `1.8e-15`。
- 四个子集各取一条真实轨迹，位姿 delta→绝对目标还原最大矩阵差小于 `8e-8`，包含单精度动作存储误差。
- 手指目标原样保留；旋转矩阵正交性、片段边界、固定 link7→link8 关系均通过。

这里验证的是提供工程的名义运动学模型和数值转换。外部安装的 `franka_description` 源包及机器人出厂标定参数没有随压缩包提供；原始采集也未同步保存可用的笛卡尔位姿真值，因此没有宣称获得实机绝对位姿精度。现有模型足以定义一致的离线训练动作表示；本次没有启动训练或控制机械臂。
